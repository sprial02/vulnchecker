# IBM TriGuard AI 고객 보고서

## RAW 데이터 통합 보관과 전달

⑧ 레포트 → **결과 동기화** 또는 **JSON 가져오기**를 완료하면 사용자별 `runtime/<PC-SID>/raw-data/<결과 ID>/<버전>/`에 자료를 모읍니다. 보고서 런타임이 준비된 상태에서는 인프라 점검 종료 후에도 자동 보관합니다. 런타임 준비 전 수집한 기존 자료는 결과 동기화로 보관하세요. 중앙 보관은 이 PC의 로컬 폴더 기준이며 원격 관리 서버의 자료를 자동 수집하지 않습니다.

**RAW 보관함**으로 폴더를 열고, 결과를 선택해 **선택 RAW ZIP 저장**을 누르면 해당 회차만 `raw-exports`에 ZIP으로 저장합니다. ZIP 또는 버전 폴더 전체를 복사하면 됩니다. 다른 고객 자료까지 포함될 수 있는 raw-data 전체를 고객에게 전달하지 마세요. 고객사명 입력은 데이터 필터가 아니며, 선택한 회차의 실제 대상을 기준으로 전달 범위를 확인합니다.

- `index.html`: 인터넷 연결 없이 여는 서버별 현황. 서버 수, 대상 수, 판정 수, 수행 실패와 상세 불완전 상태 표시.
- `checks.csv`, `assets.csv`: 필터·피벗용 전체 결과와 자산. CSV 수식 시작 문자는 보호 처리합니다.
- `checks.jsonl`: 프로그램 분석용 정규화 결과. 서버·서비스 인스턴스·프로필·항목·판정·위험도·근거·조치 내용과 회차 식별자 포함.
- `results.sqlite3`: 선택 회차만 담은 조회용 DB. 원본과 이미지 위치는 보관 폴더 기준 상대 경로입니다.
- `assessment.json`: 수행 시점, 집계, 원본 메타데이터 및 수행 제약.
- `raw/`: 원본 JSON, 서버별 ZIP/TAR 증적, 참조 이미지. 정규화 과정의 길이 제한·마스킹과 별개로 원본 바이트를 보존합니다.
- `manifest.json`: 형식 버전, 파일별 SHA256·바이트 수, 원본 누락 목록. ZIP 저장 시 해시를 검사하며, 해시는 전자서명이나 원본 수집 이전의 진위 보증은 아닙니다.

원본이 바뀐 뒤 재동기화하면 새 버전 폴더를 만들고 이전 보관본은 유지합니다. 동일 버전은 중복 복사하지 않습니다. 누락 증적을 만들어 채우거나 불완전 결과를 양호로 바꾸지 않습니다. 접속 설정·Vault·API 키 파일·vars.json·런타임 전체는 포함하지 않지만 **원본 증적 안의 계정·설정·개인정보는 그대로 포함될 수 있으므로 전달 전 검토가 필요합니다.** 원본 삭제·이동 전에 동기화가 성공했는지 확인하세요. 보관함과 ZIP은 자동 삭제하지 않으며 배포용 프로그램 ZIP에서는 제외합니다.

다른 환경에서 재보고서를 만들려면 인프라 보관본의 `raw/`를 `report-store.py --db <DB> sync-infra --root <버전 폴더>`로 색인할 수 있습니다. JSON 수집본은 `raw/` 안의 원본 JSON을 UI에서 가져옵니다. 외부 도구에서는 CSV/JSONL/SQLite를 직접 분석할 수 있습니다. 이미지 포함 JSON은 raw 폴더 전체를 함께 유지하세요.

### 2,000대 용량 산정

아래는 실측 보장이 아닌 계획용 가정입니다. 한 회차의 **대당 보관 데이터 총량(원본+DB+CSV/JSONL)**을 기준으로 계산합니다. 대당 서비스 수와 긴 명령 출력·이미지·첨부에 따라 크게 달라집니다.

| 대당 총량 | 2,000대 / 1회 | 12회 보관 |
| --- | --- | --- |
| 1~5MB | 2~10GB | 24~120GB |
| 10~50MB | 20~100GB | 240GB~1.2TB |
| 100~500MB | 200GB~1TB | 2.4~12TB |

십진 단위의 단순 곱이며, 기존 infra-runs 원본·별도 전달 ZIP·백업·임시 생성 공간은 추가입니다. 증적 ZIP/TAR는 이미 압축되어 재압축 이득이 작을 수 있습니다. 10~20대 파일럿을 보관한 뒤 `manifest.json`의 bytes 합계를 서버 수로 나눠 실측하고, 전체 회차 수·백업본 수와 생성 중 여유 공간을 반영하세요. 동일 데이터의 정규화 사본 여러 개를 포함하므로 원본 증적 파일만의 크기로 전체 저장량을 추정하지 마세요.

회차·서버·프로필·항목 기준으로 위험도/취약 항목/조치 우선순위/재점검 변화 보고서를 만들 수 있습니다. 부서·업무 중요도·담당자·조치 기한별 보고서는 해당 자산 메타데이터를 수집하거나 별도 자산대장과 연결해야 합니다. 재점검 비교는 회차 간 서버·인스턴스 식별자가 일관돼야 합니다. 수집하지 않은 과거 증적이나 실제 공격 성공 여부는 RAW 데이터만으로 복원할 수 없습니다.

## 사용 방법

1. 앱을 다시 열고 **⑧ 레포트** 탭으로 이동합니다.
2. **결과 동기화**를 누릅니다. 보고서 전용 Python과 DOCX 라이브러리가 없으면 이때 자동 설치합니다. Windows 사용자 전용 환경이며 다른 분석 도구의 Python과 분리합니다. 문서 생성에는 Word와 WSL이 필요하지 않습니다.
3. 고객사명, 작성 담당, 점검 기간과 대상 범위를 입력합니다. 종류와 결과를 선택합니다.
4. **항목 조회**에서 판정을 확인하고 **DOCX 추출**을 누릅니다. 고객사명은 모든 페이지 왼쪽 하단에 들어갑니다. 보고서 폴더 버튼으로 생성물을 확인합니다.
5. 아직 점검하지 않은 경우 **3종 서식 추출**로 모바일 앱, 웹서버, 인프라 서버 및 네트워크 보고서 서식을 만듭니다. 서식의 빈 통계는 양호 판정이 아닙니다.

모바일·웹 문서는 표지, Executive Summary, 점검 대상과 제약, 자산 및 위험도별 집계, 주요 취약점 상세, 증적, 개선 계획과 재점검 구성을 제공합니다. 인프라는 현황 파악형 점검 결과 보고서이며, 전체 판정 건수·비율·양호율과 항목별 집계 및 모든 서버의 판정 합계를 표로 표시합니다. 서버별 증적을 본문에 반복하지 않습니다. 전체 서버×항목 결과는 함께 생성하는 Excel의 「서버별 항목 결과」 시트에서 조회합니다. 헤더·서버 열 고정, 필터와 판정 색상을 지원하며 「결과 없음」은 판정 미수집 또는 범위 밖을 뜻합니다. 모바일·웹 본문 상세는 기본 30건이며 최대 200건까지 선택할 수 있습니다. 인프라는 이 제한 없이 모든 서버 집계를 포함하고, 개별 취약점 설명과 이미지는 넣지 않습니다. 전체 결과 CSV와 자산 집계 CSV는 본문 제한과 관계없이 별도로 추출합니다. 결과가 불완전하거나 담당·기간·범위가 비어 있으면 검토본으로 표시합니다. 제출 전 판정, 위험도, 실제 영향, 담당자와 조치 일정, 증적의 민감정보를 확인하십시오.

## 결과 연결

- 인프라: `infra-runs`의 기존 `summary.json`과 서버별 ZIP/TAR 증적을 동기화합니다. 보고서 런타임이 준비된 이후 수행하는 인프라 점검은 종료 시 자동 색인합니다. 접속만 확인한 사전 점검은 취약점 결과에 포함하지 않습니다. 요약과 상세가 맞지 않으면 통계의 출처를 구분하고 미완전 증적을 표시합니다.
- 모바일: 새 MobSF 정적 분석의 원본 JSON을 보관해 동기화합니다. 정적 분석 결과를 모바일 동적 분석이나 전체 API 점검 완료로 해석하지 않습니다.
- 웹 및 시스템: 새 분석 작업 안내에 `findings.json` 결과 형식이 추가됩니다. 실제 분석 도구가 작업 폴더에 이 파일을 작성한 경우 동기화로 가져옵니다. 연결 성공이나 터미널 로그만으로 취약점 결과를 만들지 않습니다. 이전 텍스트 보고서는 아래 JSON 형식으로 검토·정리한 후 가져올 수 있습니다.
- 네트워크 장비 및 외부 도구: 실제 점검 결과를 같은 JSON 형식으로 가져옵니다. 서버 점검을 수행한 것만으로 네트워크 장비 점검 완료로 표시하지 않습니다.

```json
{
  "kind": "infra",
  "name": "실제 점검 결과명",
  "metadata": {"scope": "실제 점검 범위", "limitations": "제외 또는 미확인 영역"},
  "findings": [
    {
      "id": "실제 기준 항목 ID",
      "asset": "실제 서버 또는 장비명",
      "title": "점검 항목명",
      "status": "MANUAL",
      "severity": "Unknown",
      "description": "관찰 사실",
      "impact": "근거에 따른 영향",
      "recommendation": "권고 조치",
      "evidence": "민감정보를 제거한 증적",
      "reference": "판정 기준"
    }
  ]
}
```

종류는 `mobile`, `web`, `infra`이며 판정은 `GOOD`, `VULNERABLE`, `MANUAL`, `N/A`입니다. 위험도는 `Critical`, `High`, `Medium`, `Low`, `Info`, `Unknown`입니다. 자동으로 CVSS나 미입력 위험도를 만들어 넣지 않습니다. 같은 항목이 여러 자산에 존재하면 자산별 건수로 집계합니다. 양호율은 양호 ÷ (양호 + 취약)이며 수동 확인과 해당 없음은 제외합니다.

수동 가져오기에서는 항목의 `images` 배열에 `{"path":"evidence/screen.png","caption":"실제 증적 설명"}`을 추가할 수 있습니다. 이미지는 JSON 폴더 내부의 PNG/JPEG이며 파일당 10MB 이하, 항목당 최대 10개입니다. 가져온 후 파일이 변경되면 해당 이미지를 문서에 넣지 않습니다. WSL 결과 자동 동기화는 텍스트 증적을 가져옵니다. 이미지가 필요하면 JSON과 이미지 폴더를 함께 Windows에 복사해 수동 가져오기를 사용하십시오.

## DB와 대규모 인프라 결과

사용자별 runtime의 `report-results.sqlite3`에 결과명, 자산, 판정, 항목과 증적 위치를 저장합니다. SQLite를 내장하므로 별도 DB 서버 설치가 필요 없습니다. WAL과 색인을 사용하고 화면은 100건씩 조회하며 CSV는 행 단위로 생성합니다. 문서 생성은 읽기 트랜잭션으로 동일한 시점의 결과를 사용합니다. 동일 인프라 실행은 재동기화해도 중복되지 않습니다. JSON 가져오기는 실패하면 이전 결과를 보존합니다.

원본 증적 압축 파일은 DB와 별도로 유지하십시오. 백업 시 앱 작업을 종료한 뒤 DB와 관련 원본·이미지를 함께 보관하십시오. 여러 PC가 동시에 공동 저장소에 쓰는 운영이 필요하면 중앙 PostgreSQL 등과 수집 API로 확장할 수 있습니다. 현재 DB는 한 Windows 앱의 로컬 결과 관리를 위한 구성입니다.

문서와 CSV의 텍스트 증적에서 흔한 인증 헤더·쿠키·비밀번호·토큰을 마스킹합니다. 이미지와 모든 형태의 개인정보까지 자동 제거하지는 않으므로 고객 제출 전에 검토해야 합니다. 고객 결과, DB와 런타임은 배포 ZIP에 포함하지 않습니다. 공개된 세 가지 DOCX는 실제 점검 수치가 없는 고객사명 자리표시 서식입니다.

보고서는 **물리 서버 수**와 **OS/서비스 점검 대상 수**를 구분합니다. 동일 서버 OS·WAS·DB 결과는 별도 행이며, MySQL D-01과 Oracle D-01처럼 다른 프로필의 항목 ID가 같아도 합치지 않습니다. Excel의 다른 프로필 열은 ‘범위 외’, 같은 프로필의 미수집 결과는 ‘결과 없음’으로 표시합니다. 판정을 임의로 양호나 해당 없음으로 대체하지 않습니다.
