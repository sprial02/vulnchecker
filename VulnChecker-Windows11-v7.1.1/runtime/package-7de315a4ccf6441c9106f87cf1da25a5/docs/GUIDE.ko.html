모바일 앱: 추출부터 펜테스트까지
  1. ① 앱 추출 / 루팅 기기 설치를 누르면 기존 ④ 앱 가져오기 탭이 열립니다. Google Play 기기/실제 단말/고객 APK에서 전체 APK를 확보하고 루팅 분석 기기에 설치합니다. 기본 실행 확인은 Frida 루팅 우회를 적용합니다.
  2. ② 설치 앱 찾기 / 새로고침으로 분석 기기에 설치된 대상 앱을 선택합니다.
  3. ③ MobSF는 선택 앱 정적 보고서와 동적 분석, 앱 API(Burp)는 선택 앱의 통신 수집을 준비합니다.
  4. ④ 모바일 앱 펜테스트 연결은 선택 앱의 전체 APK, 원본 서명/해시, 전용 ADB 연결을 Kali에 준비하고 MCP에서 실제 앱 경로를 확인한 뒤 모바일 OpenCode를 엽니다. MOBILE_TARGET.md를 읽고 APK/API 점검 범위를 지정하세요. API 요청/응답은 Burp 또는 MobSF에서 내보내 작업 폴더에 저장합니다.

HexStrike는 준비된 APK와 adb-target을 통해 앱에 접근합니다. Frida 주입 자체는 모바일 메뉴에서 수행합니다.

시스템(IP/URL) 펜테스트

IP/URL을 지정하고 실행하면 별도 CMD와 OpenCode를 엽니다. 시스템 작업 폴더는 모바일 폴더와 분리합니다. 웹 프록시 점검이 필요하면 Burp 포함 버튼을 사용합니다. 연결 준비와 실제 취약점 점검 완료는 구분합니다.

실행 순서

화면 아래 진행 막대에서 전체 설치 진행률, 완료한 단계 수와 현재 설치 항목을 확인합니다. 예: 설치 44% · 4/9 단계 완료 · Docker Desktop 설치 중. 비율은 완료한 설치 단계 기준이며 파일의 다운로드 비율이나 남은 시간은 아닙니다. 실패한 단계는 완료로 계산하지 않으며 재부팅 필요·중지 상태를 구분하여 표시합니다.

  1. 프로그램 폴더 전체를 고객사 PC의 쓰기 가능한 로컬 폴더로 복사합니다. ZIP 파일 내부에서 실행하지 않습니다. 이전 고객사 runtime 폴더는 전달하지 않습니다.
  2. Start.cmd를 더블클릭합니다. GUI는 일반 권한으로 열고 설치 작업만 승격하는 방식이 권장됩니다.
  3. 기존 설치 / 사전 확인을 누릅니다. 설치 경로·Kali 기존 사용자·SDK/AVD·Docker 설치를 먼저 확인하고, 추가 설치 후보에 대해서만 용량을 계산합니다. Windows 버전·가상화·권한도 함께 확인합니다.
  4. 필요하면 설정 파일에서 config.json을 수정합니다. 다음 작업부터 설정이 반영됩니다. 기본 full 프로필은 웹+Android 전체입니다.
  5. 새 PC는 자동 설치 / 이어하기로 사전 확인부터 누락 도구 다운로드·설치까지 진행합니다. 확인 버튼만 누르면 설치하지 않습니다.
  6. 공식 약관 링크를 검토한 뒤 동의란을 선택하고 자동 설치 / 이어하기를 누릅니다. UAC에서 현재 사용자 계정으로 승인합니다. 다운로드는 백그라운드에서 진행되며 아래 로그에서 상태를 확인합니다.
  7. 재부팅 필요가 표시되면 작업을 저장하고 Windows를 재부팅합니다. 같은 Windows 계정에서 Start.cmd → 자동 설치 / 이어하기를 다시 실행합니다. 이미 설치된 프로그램과 검증된 Kali 도구는 재사용합니다.
  8. Docker 첫 실행 시 약관·로그인·WSL 관련 화면이 나오면 완료합니다. “Linux containers” 모드가 필요합니다. 준비 시간이 초과되면 Docker 정상화 후 이어하기를 다시 실행합니다.
  9. 설치 상태 확인에서 설치됨·설치됨/준비 필요·미탐지·미확인을 확인합니다. Docker 엔진에 연결할 수 없는 경우 이미지 미설치로 단정하지 않습니다. 설치 프로그램은 종료 시 이 가이드를 자동으로 엽니다.
  10. ② 실행 / 연동에서 ① 모바일 앱 MobSF 정적/동적 분석 실행 또는 ② Penetration Test 실행을 한 번 누릅니다. 필요한 서비스 시작과 연동 검사가 순서대로 진행되고 ③ 연동 결과가 자동으로 열립니다. 모바일은 OpenCode와 ADB 명령 창, Penetration Test는 OpenCode 명령 창만 열립니다.
재부팅은 자동으로 하지 않습니다. 환경에 따라 여러 번 필요할 수 있습니다. Start.cmd를 같은 계정으로 다시 실행하면 이어서 설치할 수 있습니다. 한 항목이 실패하면 다른 독립 항목은 진행하고 의존하는 항목은 실행하지 않습니다.

루팅과 MobSF 동적 분석

모바일 앱 MobSF 정적/동적 분석 실행 메뉴은 전용 AVD를 -writable-system -no-snapshot으로 부팅하고 다음을 확인합니다.

  1. Android 부팅 완료와 설정 API 일치
  2. adb root 후 실제 UID 0
  3. 전용 AVD의 AVB/verity 해제 및 재부팅, remount
  4. /system에 임시 파일 생성·삭제 성공
  5. MobSF 웹 응답 및 컨테이너에서 host.docker.internal:5555로 ADB 연결
  6. 컨테이너 ADB를 통한 UID 0과 /system 쓰기 성공

실기기나 다른 AVD에는 루트 준비 명령을 실행하지 않습니다. 에뮬레이터 데이터 초기화(wipe-data)도 수행하지 않습니다. 기존 5554/5555 포트가 사용 중이면 해당 에뮬레이터를 종료해야 합니다.

MobSF에서 실제 분석하기

앱의 루팅 차단 안내가 뜨는 경우

실행/연동 탭의 분석 앱에 패키지명을 입력하고 루팅 우회 후 앱 실행을 누르세요. 통신 경로 준비 후 앱을 Frida로 새로 실행합니다. 에너지플러스 8.9(versionCode 234)는 확인된 루팅 검사 5개에 별도 후크를 적용합니다. 다른 버전의 검사 위치는 다시 확인해야 합니다. 서명·TLS·Play 무결성은 별도입니다.

우회 세션 종료는 관리 Frida 세션만 해제합니다. MobSF Dynamic Analyzer로 전환할 때는 이 세션을 먼저 종료하고 Bypass Root Detection을 선택하세요. 앱 가져오기의 프로세스 확인은 루팅 차단 통과를 뜻하지 않습니다.

통신 경로는 MobSF → Burp와 MobSF 직접 수집 중 선택합니다. 현재 PC의 에너지플러스는 Burp 경유 시 JavaScript 응답 중단으로 흰 화면이 나타날 수 있습니다. MobSF 직접 수집 (Burp 전달 없음)으로 시작 화면과 API 수집을 확인했습니다. 직접 수집에서는 MobSF/HTTPTools에서 통신을 확인하며 Burp에 전달하지 않습니다. 관리 capture는 HTTP/1.1을 사용합니다.

  1. 열린 MobSF에서 최초 계정 mobsf / mobsf로 로그인합니다. 고객사 운영 기준에 따라 비밀번호를 변경합니다.
  2. 승인된 APK를 업로드하여 정적 분석을 완료합니다.
  3. 해당 APK의 Dynamic Analyzer 화면에서 분석을 시작합니다. 앱 설치와 Frida 계측 결과를 확인하고 허용된 진단 시나리오를 수행합니다.
  4. 분석 종료 후 결과를 내보내고 정리합니다. 시작 실패 시 MobSF 로그, APK ABI·SDK 요구사항, 네트워크 및 Frida 버전을 확인합니다.

MobSF는 분석 중 자체 Frida 서버와 프록시를 준비합니다. Kali의 Frida/Objection은 별도 수동 분석용이며 독립적으로 설치됩니다. 수동 Frida를 사용하는 경우 클라이언트·서버 버전을 맞추고 APK의 x86_64/ARM 호환성을 확인해야 합니다. ADB root는 Magisk/su 기반 루팅과 다르므로 앱별 루팅 탐지나 su 요구사항이 동일하게 동작하지 않을 수 있습니다.

MobSF와 Burp를 함께 쓰려면 모바일 앱 MobSF 정적/동적 분석 실행 메뉴를 선택하세요. 이 메뉴에 프록시 연동이 포함됩니다. Android → MobSF 1337 → Burp 8080 순서로 전달하며, MobSF가 앱 분석을 시작해도 같은 upstream 설정을 사용합니다. 개별 CLI 흐름을 실행하면 Android 프록시가 바뀔 수 있습니다. 앱의 인증서 고정 우회는 자동화하지 않습니다.

MobSF 정적 ↔ 동적 모드 변경: 모바일 메뉴는 필요한 동적 모드로 자동 재구성합니다. 실행 중인 분석은 먼저 저장하세요. 관리 서비스 중지는 연동 결과 탭에 있습니다. 컨테이너만 필요한 설정으로 재생성하고 분석 데이터 볼륨은 유지합니다.

HexStrike와 OpenCode 연결

  1. 두 가지 분석 메뉴 중 하나를 누르면 Burp/모바일 준비 이후 AI 연동이 자동으로 진행됩니다. HexStrike 서버가 먼저 시작됩니다. 같은 포트의 기존 서버는 HexStrike 응답을 확인한 뒤 재사용합니다.
  2. 탐지한 Kali 사용자와 Python/소스 경로로 프로젝트 ~/work/vulnchecker/opencode.json의 mcp.hexstrike.enabled=true를 자동 설정합니다. 기존 JSON은 변경 전에 같은 폴더에 백업하고 다른 MCP/provider 설정을 보존합니다. JSON 파싱 실패는 덮어쓰지 않고 오류로 표시합니다.
  3. 서버 /health → MCP initialize/list_tools → OpenCode 자체 mcp list 순서로 검사합니다. 도구 개수는 로그에 표시됩니다. MCP 검사 중 도구 호출이나 대상 스캔은 하지 않습니다.
  4. OpenCode 화면에서 /connect로 고객사가 허용한 AI 계정/모델을 연결합니다. 이미 열려 있던 OpenCode는 새 설정을 읽도록 다시 실행합니다. 연결 결과의 AI 계정 “사용자 확인”은 MCP 실패가 아니라 모델 인증이 별도라는 뜻입니다.
Penetration Test 실행은 Burp와 OpenCode를 함께 시작합니다. Windows Burp의 GUI/API를 HexStrike가 직접 제어하는 구성은 아닙니다. HTTP 분석은 Burp에서, Kali 도구 실행은 OpenCode의 HexStrike MCP에서 수행합니다. API 키는 config.json에 넣지 않습니다.

Android + Burp 연동

전용 AVD 부팅 → root/remount → Burp 실행 → proxy 응답 및 CA 다운로드 → 전용 AVD의 시스템 CA 설치 → ADB reverse 8080 → Android proxy 설정 → 실제 HTTP 응답 검사까지 수행합니다. Windows 인증서 저장소는 변경하지 않습니다. Burp 첫 실행은 약관/Temporary project/Start Burp를 완료해야 합니다. 연결 대기는 2분입니다. Intercept가 켜져 있으면 요청을 Forward하거나 끄고 테스트 앱 트래픽을 확인하세요.

Burp Community는 실행 옵션 --config-file로 설정 선택 화면을 줄입니다. Temporary project → Next → Start Burp는 직접 완료해야 합니다. Community의 프로젝트 화면 전체 생략은 공식 지원 옵션으로 보장하지 않습니다. 기존 설정을 덮어쓰는 --use-defaults는 사용하지 않습니다.

MobSF + Burp 동시 분석 순서

  1. 진행 중 분석을 저장하고 실행 탭의 MobSF + Burp를 누릅니다. 정적 모드가 실행 중이면 관리 서비스 중지 후 다시 실행합니다.
  2. Burp 초기 화면을 완료하고 Proxy → Intercept Off로 설정합니다. 8080 listener가 필요하며 처음 시작할 때 최대 2분 기다립니다.
  3. 프로그램이 MobSF upstream을 구성합니다. 설정이 변경되면 관리 컨테이너를 재시작하고 저장된 분석 볼륨은 유지합니다. ADB/root/Frida와 MobSF CA 설치를 검증합니다.
  4. 연동 결과에서 Frida server, MobSF CA, MobSF + Burp, Android → Burp 전달 검사를 확인합니다. Burp Proxy → HTTP history에서 범위 필터를 해제하고 /login/?vulnchecker-check=... 요청을 찾습니다. 이 요청은 PC의 MobSF 로그인 페이지로 보내는 로컬 HTTP 검증이며 외부 사이트나 고객 API를 호출하지 않습니다.
  5. MobSF에서 승인된 APK를 업로드하고 Dynamic Analyzer를 시작합니다. 실제 앱 통신을 MobSF와 Burp에서 확인합니다. 위 검증은 HTTP 전달 성공이며 앱 HTTPS/pinning 성공까지 보장하지 않습니다.
  6. MobSF 단독으로 돌아가려면 MobSF 동적 연동을 누릅니다. Burp upstream을 해제하고 변경 시 컨테이너를 재시작합니다.

앱 종료 진단 · Frida · 루팅 우회

  1. 추가 앱 진단은 CLI VulnChecker.ps1 -Action Launch -Tool AppDiagnostics -Package com.company.app으로 실행합니다. MobSF가 실행 중이고 앱이 설치되어 있어야 합니다. 설치 APK의 native library와 crash 로그를 확인합니다.
  2. librealm-jni.so가 없으면 고객사에서 전체 split APK 세트 또는 해당 라이브러리가 포함된 universal APK를 받으세요. 같은 버전/서명으로 필요한 ABI split을 포함해야 합니다. base APK 하나만으로 설치된 앱의 누락 라이브러리를 JS로 고칠 수 없습니다. 이 오류는 루팅 탐지라고 단정하지 않습니다.
  3. 모바일 메뉴의 Frida 준비 단계는 MobSF 클라이언트와 서버 버전·ABI를 맞춥니다. 프로세스 조회뿐 아니라 root/full access와 설정 앱 spawn/attach를 확인합니다. 최초 검증 때 Android 설정 화면이 잠깐 열릴 수 있습니다.
  4. CLI VulnChecker.ps1 -Action Launch -Tool RootBypass -Package com.company.app은 지정한 앱을 spawn → attach → JS load → resume 순서로 시작합니다. 실제 Java 후크 초기화 메시지가 있어야 주입 확인으로 표시합니다. 앱 종료 시 runtime의 frida-패키지-out.log/error.log와 앱 진단 결과를 확인하세요.
  5. 기본 JS는 Build.TAGS, 일부 su 파일 존재 검사, RootBeer boolean 검사를 다룹니다. 다른 탐지, 에뮬레이터 탐지, Play Integrity, native 탐지와 TLS pinning은 앱별 추가 검증이 필요합니다. 수정 위치는 scripts/root-bypass.js입니다.
  6. MobSF 분석에서는 Bypass Root Detection을 선택한 상태로 계측을 시작하세요. 모바일 자동 준비가 MobSF 기본 root_bypass에 추가 JS를 연결하므로 같은 분석 세션에서 실행됩니다. Frida 로그의 VulnChecker Java root hooks loaded 메시지로 실제 초기화를 확인합니다. 별도 루팅 우회 실행은 수동 분석용입니다. MobSF 수집 중 다시 spawn하면 기존 계측이 끊길 수 있습니다. 관리 서비스 중지는 관리 수동 세션도 종료합니다.

이 PC에서는 Frida 17.18 ART helper 및 17.7.1 linker 충돌을 발견하여 MobSF/서버를 16.7.19로 맞춘 뒤 실제 Java 후크 주입을 확인했습니다. 알려진 17 ART/linker 오류가 발생하면 공식 기반 이미지에서 호환 이미지를 자동 생성합니다. 원본 이미지는 유지하고 분석 데이터는 기존 볼륨에 남습니다. 이 버전 고정은 해당 환경의 검증 결과이며 모든 기기에서의 호환성을 보장하지 않습니다. Kali Frida/Objection은 별도 클라이언트이므로 수동 연결 시 같은 서버 버전으로 맞춰야 합니다.

winget 없음 / 설치 차단자동 설치가 Microsoft App Installer 등록 및 WinGet 다운로드·설치를 먼저 진행합니다. 실패하면 연동 결과의 단계별 오류를 확인하세요. Microsoft/PowerShell Gallery 접근 또는 Windows 앱 설치 정책이 차단된 경우 고객사 IT 확인이 필요합니다.

SDK/Java 없음설치 탭에서 설치/이어하기. Studio 없이 Microsoft OpenJDK 21 + SDK를 준비합니다. 기존 Java/JBR은 재사용합니다.
Android가 안 올라옴전용 AVD가 없으면 설치된 이미지로 새로 만듭니다. 이미지까지 없으면 설치 탭을 먼저 실행하세요. 소프트웨어 GPU, RAM 2GB, CPU 2개로 실행하며 프로세스 종료 시 즉시 원인을 표시합니다. runtime의 emulator-stdout.log / emulator-stderr.log에서 디스크/가상화/이미지 오류를 확인합니다. 자동 wipe-data는 하지 않습니다.

컨테이너 ADB 연결 실패host.docker.internal:5555 접근과 Docker Desktop 네트워크/보안 정책 확인. 프로그램은 자동 방화벽 예외나 외부 공개 portproxy를 만들지 않음.
APK 설치/실행 불가minSdk, ABI, Google Play 의존성 확인. 실제 앱의 시스템 요구사항이 Android 11과 맞는지 확인. 에뮬레이터가 모든 실기기 시나리오를 대체하지 않음.
다운로드 중 중단 / 부분 실패네트워크 복구 후 전체 설치/이어하기. 실패한 단계 상태를 기록하며 완전 설치로 표시하지 않음. 손상 SDK latest 폴더는 해당 폴더를 다른 이름으로 이동 후 재시도.

망분리·반복 배포

기본 프로그램은 온라인 설치용이며 완전 오프라인 번들은 제공하지 않습니다. 같은 PC에서는 설치/검증 결과를 재사용합니다. 여러 고객사 PC에서 시간을 더 줄이려면 승인된 도구만 담은 Kali 이미지를 준비하여 wsl --export하고 kaliImportTar로 배포할 수 있습니다. Docker도 승인된 이미지를 docker save하여 mobSfImageTar로 전달할 수 있습니다.

그러나 Kali 도구 bootstrap, SDK, Windows 설치 파일은 기본 흐름에서 온라인 저장소가 필요할 수 있습니다. 완전 망분리라면 고객사 IT의 사전 설치 또는 apt/npm/pip/SDK 내부 저장소와 검증된 이미지 배포 설계를 별도로 준비해야 합니다. 프록시 인증정보를 배포 파일에 저장하지 마세요.

작업 종료와 고객사 PC 반납

  1. Burp/MobSF 보고서와 프로젝트를 고객사에서 승인한 위치에 저장합니다.
  2. 관리 서비스 중지로 MobSF 및 이 프로그램이 실행한 에뮬레이터를 중지합니다. 관리 HexStrike 백그라운드 서버도 종료합니다. Burp/OpenCode/ADB 창은 직접 닫습니다.
  3. AI 공급자 인증을 사용했다면 해당 공급자의 로그아웃/토큰 해지 절차를 수행합니다. 인증은 Kali 사용자 홈의 앱별 저장소에 남을 수 있습니다.
  4. 고객사 보존/삭제 기준에 따라 APK·분석 결과·토큰·로그·도구 환경을 정리합니다. 기본 중지 버튼은 데이터를 삭제하지 않습니다.

고객사 승인 후 수동 제거 예

아래는 해당 환경과 분석 데이터의 영구 삭제 명령입니다. 결과 백업과 배포판/볼륨 소유를 확인한 뒤 필요한 항목만 수행하세요. 기존 고객사 Kali를 사용했다면 그 배포판을 unregister하지 마세요.

docker rm vulnchecker-mobsf
docker volume rm vulnchecker-mobsf-data
# 전용으로 만든 Kali만 삭제. 사용자 데이터도 모두 삭제됩니다.
wsl --unregister kali-linux

SDK/AVD는 %LOCALAPPDATA%\VulnChecker\Android, import한 배포판 경로는 %LOCALAPPDATA%\VulnChecker\WSL입니다. Windows 앱은 설정 → 설치된 앱에서 고객사 기준에 따라 제거하세요. Docker/WSL 및 다른 고객사 앱을 일괄 제거하지 않습니다.
